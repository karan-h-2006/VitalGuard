## 1. Introduction: Why Engineering Maturity Means Acknowledging Limits

In software engineering evaluations, examiners rarely penalize students for having system limitations. What _does_ tank grades is pretending those limitations do not exist or attempting to bluff when an examiner spots an architectural shortcut.

VitalGuard is a functional, full-stack, enterprise-patterned prototype designed, engineered, and verified within academic deadlines. In any real-world engineering project, building under finite time and resource constraints requires making **deliberate engineering trade-offs**.

This document catalog's VitalGuard's known architectural limitations, explains the root causes and real-world implications of each, details the exact production-grade mitigations, and provides a coaching guide on how to articulate these points with confidence during your viva.

## 3. Deep Dive into Architectural Limitations

### 3.1 Security and Authentication Architecture

#### JWT Storage in Browser `localStorage`

- **Current Implementation**: When a user logs in, the Fastify API returns a signed HS256 JWT in the JSON response payload. The React frontend (`apps/web/src/context/AuthContext.tsx`) persists this string in `window.localStorage` under the key `vg_token`.
- **The Risk**: While convenient for Single Page Applications (SPAs) and multi-tab state persistence, `localStorage` has no cross-context isolation against JavaScript execution. If an attacker manages to execute an XSS payload via an unescaped clinical note or patient name, the script can simply call `localStorage.getItem('vg_token')` and exfiltrate credentials.
- **Production Solution**: Migrate to an `httpOnly`, `Secure`, `SameSite=Strict` cookie architecture. The browser automatically attaches the cookie to outbound API requests, but JavaScript is strictly barred from reading the cookie string. To safeguard against Cross-Site Request Forgery (CSRF), pair the cookie with double-submit CSRF tokens or custom request headers (`X-Requested-With`).

#### In-Memory Rate Limiting

- **Current Implementation**: The API enforces brute-force protection using a custom in-memory JavaScript `Map` (`apps/api/src/plugins/rate-limiter.ts`). It tracks failed authentication attempts keyed by IP and email, locking out accounts after 3 failures (Admin) or 5 failures (Doctor/User).
- **The Risk**: Because state resides exclusively in Node.js process heap memory, restarting the API process instantly flushes all rate-limiting counters. More critically, if the API is scaled horizontally across 3 worker containers behind an NGINX load balancer, an attacker's attempts are distributed across containers, tripling the allowed brute-force budget.
- **Production Solution**: Migrate to a distributed sliding-window rate limiter powered by Redis. Using Redis commands like `MULTI`, `ZADD`, and `EXPIRE` (or an established library like `rate-limiter-flexible`), all API instances share a single, authoritative rate-limiting state that survives process restarts.

#### Lack of Two-Factor Authentication (TOTP)

- **Current Implementation**: Authentication requires only an email address and an Argon2id-hashed password. While schema discussions considered multi-factor fields, active user onboarding and login flows do not require a secondary factor.
- **The Risk**: Healthcare systems are prime targets for credential stuffing and phishing attacks. Compromising a single physician password grants unauthorized access to sensitive patient clinical telemetry.
- **Production Solution**: Implement RFC 6238 TOTP using libraries such as `speakeasy` or `otplib`. During onboarding, users scan an `otpauth://` QR code into an authenticator app (Google Authenticator, Bitwarden). The login route then requires a 6-digit TOTP token before issuing the final JWT.

### 3.2 Real-Time Telemetry Streaming & Scalability

#### WebSocket Redis Polling vs. Event-Driven Push

- **Current Implementation**: The Fastify WebSocket endpoint (`GET /ws?token=...`) sets up a 500ms `setInterval` timer per active client socket. Every 500ms, the server queries the Redis key `patient:<id>:status`, parses the JSON, compares it with the previous snapshot, and emits a frame if values differ.
- **The Risk**: While this design decoupled the API from worker ingestion bursts and simplified prototype delivery, polling creates an active execution loop on the Node.js event loop for every connected browser tab. With 1,000 active clinicians, the API executes 2,000 Redis queries per second regardless of whether patient vitals have actually changed.
- **Production Solution**: Transition to an event-driven pub/sub architecture. When the Python worker calculates a new severity status, it publishes an event to a Redis Pub/Sub channel (`patient:events:<id>`). The Fastify API subscribes to these channels and pushes frames down the WebSocket immediately upon receipt, dropping idle CPU overhead to near zero.

#### PostgreSQL as a Time-Series Telemetry Store

- **Current Implementation**: Raw telemetry readings are inserted directly into the standard PostgreSQL table `vital_readings`. The table uses composite indexes on `(patient_id, vital_type, timestamp)`.
- **The Risk**: At 1 reading per second across 4 vitals for 100 patients, the database ingests 34.5 million rows per day. In standard PostgreSQL, table and index bloat degrade query performance over time, and routine VACUUM operations consume heavy I/O bandwidth.
- **Production Solution**: Transform PostgreSQL into a true time-series database using the **TimescaleDB** extension. Converting `vital_readings` into a _Hypertable_ automatically partitions data into time-based chunks, enables columnar compression (achieving 90%+ storage reduction), and allows automatic data retention drops for telemetry older than 90 days.

### 3.3 Persistence, Reporting & Edge Hardware

#### Local Disk Storage for PDF Summaries

- **Current Implementation**: The automated reporting cron job (`node-cron` running Sunday midnight) and on-demand report routes use `PDFKit` to render clinical summaries directly into the local filesystem directory `apps/api/generated-reports/`.
- **The Risk**: In a containerized cloud deployment (e.g., AWS ECS, Kubernetes), containers are ephemeral. If an API container restarts, locally generated PDFs are lost. Furthermore, if a user requests a download routed to Node Container B, but Node Container A generated the file, the download fails with a 404 error.
- **Production Solution**: Stream generated PDF byte buffers directly to an S3-compatible object store (Amazon S3, Cloudflare R2, or MinIO). The database `reports` table stores the immutable object key, and the API generates a pre-signed, time-limited URL (e.g., expiring in 15 minutes) when a clinician clicks "Download Report".

#### Synthetic vs. Physical IoT Hardware

- **Current Implementation**: The system ingests telemetry generated by `simulator/manager.py`. While the simulator realistically models physiological dynamics (tachycardia, hypoxia, sensor noise, and disconnects), it generates clean, uniform packets.
- **The Risk**: Real medical edge hardware experiences physical signal degradation: skin detachment, motion artifacts (shaking hands), battery voltage drops, Wi-Fi reconnection handshakes, and out-of-order packet delivery.
- **Production Solution**: Connect a physical microcontroller (such as an ESP32 or Raspberry Pi Pico W) wired to a MAX30102 pulse oximeter and DS18B20 digital temperature probe. The microcontroller firmware flashes data formatted to `schemas/vital-sample.schema.json` over Wi-Fi directly to Mosquitto MQTT.

### 3.4 API Documentation & Test Coverage

#### OpenAPI Specification Drift

- **Current Implementation**: The REST documentation in `apps/api/openapi/openapi.yml` was manually authored during early system design. As development accelerated, several new endpoints were added to Fastify routes but omitted from the YAML file (notably `GET /ws`, `/vitals/history`, `/patients/:id/reports`, and `/patients/:id/thresholds`).
- **The Risk**: Third-party developers or client engineering teams relying on the OpenAPI specification encounter undocumented routes or outdated request/response schemas.
- **Production Solution**: Eliminate manual YAML authoring. Configure `@fastify/swagger` and `@fastify/swagger-ui` to inspect Fastify's native JSON route validation schemas and compile the OpenAPI 3.1 specification dynamically at runtime or build time.

#### Automated Integration and Load Testing

- **Current Implementation**: VitalGuard includes unit tests (Vitest) for authentication hashing, password rules, and isolated analytics functions. However, end-to-end integration flows (e.g., simulating 500 concurrent WebSocket clients or verifying PDF layout rendering) require manual verification.
- **Production Solution**: Introduce a comprehensive testing pyramid:
  - **E2E Browser Tests**: Use Playwright to simulate patient registration, admin doctor approval, threshold overrides, and live WebSocket graph updates.
  - **Load Testing**: Use `k6` to stress-test the ingestion bridge, RabbitMQ queues, and WebSocket connections up to 5,000 simulated devices.

## 5. How to Answer Honestly Without Tanking Your Grade

When an examiner points out an architectural flaw, your response determines whether they view you as an amateur who cut corners or as a mature software engineer who made informed, deliberate trade-offs.

### The 3-Step "A+ Defense" Formula

1. **Acknowledge Immediately (Never Bluff)**: Validate the examiner's observation right away. Use words like _"That is an accurate observation,"_ or _"Yes, that is an acknowledged architectural trade-off in our current build."_ Never attempt to defend a known vulnerability as "working as intended."
2. **Explain the Pragmatic Academic Context**: Explain _why_ the choice was made during this development cycle. Highlight that the priority was establishing a working end-to-end pipeline (Edge $\rightarrow$ Queue $\rightarrow$ Analytics $\rightarrow$ WebSocket $\rightarrow$ UI) within project deadlines rather than premature multi-cloud optimization.
3. **Present the Production Solution with Technical Specifics**: Immediately describe the exact industry-standard solution. Name the specific tools, protocols, and architectural patterns you would use.

### Coaching Vignettes: Real Examiner Scenarios

#### Scenario A: The Examiner Asks About `localStorage` JWTs

> **Examiner:** _"I see you are storing your JWTs in localStorage. Don't you know any cross-site script can steal the doctor's credentials? Why didn't you use httpOnly cookies?"_
>
> **Your Coached Answer:**  
> _"You are completely right, sir. In this academic prototype, we chose `localStorage` to expedite rapid SPA development and simplify state synchronization across browser tabs without having to configure complex local CORS and cookie domain policies. However, we have thoroughly documented this in our limitations log as an XSS vulnerability. In a production hospital release, we would store authentication tokens in `httpOnly`, `Secure`, `SameSite=Strict` cookies paired with a Redis-backed refresh token rotation strategy, ensuring client scripts cannot access token bytes."_

---

#### Scenario B: The Examiner Asks About WebSocket Redis Polling

> **Examiner:** _"Your WebSocket endpoint runs a 500ms `setInterval` polling Redis. That doesn't scale. Why didn't you use true push?"_
>
> **Your Coached Answer:**  
> _"Yes, that is an intentional trade-off. Polling Redis every 500ms allowed us to completely decouple the API layer from telemetry ingestion spikes, gave us natural deduplication by comparing hash states before emitting frames, and made debugging straightforward during our sprints. However, we recognize that connection-per-client polling consumes unnecessary CPU cycles at scale. Our documented production roadmap replaces this polling loop with a Redis Pub/Sub subscription pattern, allowing the API to push frames only when the Python worker publishes an event."_

---

#### Scenario C: The Examiner Asks About Simulated Data

> **Examiner:** _"You don't have any real IoT hardware here. Isn't this just a mock website?"_
>
> **Your Coached Answer:**  
> _"While our sensor inputs are synthetically generated, every layer of the downstream data pipeline is 100% production-grade and real. The telemetry is published over standard Mosquitto MQTT using a strict clinical JSON schema, routed through RabbitMQ message brokers, analyzed in real time by a statistical Python worker, stored in PostgreSQL, and pushed live over WebSockets to our React application. The only simulated component is the physical skin contact. If we plug in an ESP32 microcontroller with a MAX30102 pulse sensor tomorrow, it communicates with the exact same MQTT topic and payload format without changing a single line of backend code."_
